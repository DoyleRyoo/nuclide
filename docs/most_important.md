# 앱을 공개하기 전에 직접 정하셔야 할 결정 정리 (검증 1~3차 기준)

검증 1~3차에서 사실 확인은 대부분 끝났습니다. 남은 것은 대부분 **누구를 위해 무엇을 책임질지 정하는 일**입니다. 아래는 제가 대신 정할 수 없고, 정해 주셔야 다음 단계가 진행되는 항목들입니다.

## 1. 가장 먼저 정할 것: 다른 결정이 모두 여기에 달려 있습니다

**① 목표 사용자 1·2순위**
- 검증 문서 공통 B-1의 이 칸이 아직 비어 있습니다. 그래서 1~3차 모두 사용자군별 가중치를 두지 못했습니다.
- 이게 정해져야 다음이 결정됩니다.
  - 감마 역검색, 단면적, 인용 복사 같은 기능이 필수인지 선택인지
  - 실사용자 시험에 누구를 모집할지
  - 수정 우선순위
- 선택지 예: 교육(학생·교사), 방사화학, 핵물리, 질량분석, 감마분광, 핵의학, 원자로
- 근거: [1차 01 §1](docs/conformity-inspection-2026-10-02/01-data-science.md)

**② 출시 목표 단계와 범위**
- 현재 판정은 "교육용 진입 전"입니다.
- 목표 단계를 골라 주셔야 합니다. 단계마다 필요한 조건이 다릅니다.
  - 교육용
  - 입문자용
  - 연구 보조 도구: 필드별 출처·인용, 원문 오기 정리가 추가로 필요합니다.
  - 전문 연구용: 방출선 데이터와 업데이트 체계까지 필요합니다.
- v1 범위(지도와 기본 성질만 제공)를 유지할지도 함께 정해야 합니다.
- 근거: [1차 03 §4](docs/conformity-inspection-2026-10-02/03-verdict.md)

## 2. 데이터 정책: 과학자가 믿고 쓸 수 있는지가 여기서 정해집니다

**③ NUBASE2020 원문 자체의 오기 12건 처리**
- 화면에 틀린 값이 그대로 나옵니다.
  - ¹⁶⁴Ho: β⁻가 β⁺로 표기됨
  - ¹⁸²Pt: 분기비 99.962 %가 0.962 %로 표기됨
  - 불확도 자릿수 오류 7건
- 선택지는 셋입니다.
  - 그대로 두기
  - 근거를 붙인 별도 정정 목록으로 고치기. `data/raw`는 그대로 두는 원칙은 지킵니다.
  - 고치지 않고 "원문 오기 가능" 표시만 하기
- 원문과 다른 값을 내보내는 책임은 개발자가 지게 됩니다.
- 근거: [2차 03](docs/conformity-inspection-2026-10-02-r2/03-source-data-errors.md)

**④ 단일 평가본 고정 vs 최신 측정 반영**
- 12개 핵종은 NUBASE2020 이후 측정으로 값이 크게 바뀌었습니다. 예: ²⁴⁹No가 앱에서는 57 μs, 현재 ENSDF에서는 38.1 ms입니다.
- 선택지는 셋입니다.
  - NUBASE2020로 일관성을 유지하고 차이를 표시만 하기
  - ENSDF 최신값으로 부분 교체하기. 이 경우 출처가 섞입니다.
  - 차기 NUBASE 평가본이 나올 때까지 기다리기
- 근거: [3차 03](docs/conformity-inspection-2026-10-02-r3/03-newer-evaluations.md)

**⑤ 존재비 기준과 표시**
- 기준값 선택: 앱은 IUPAC 2013 값을 씁니다. CIAAW 최신값과는 Pb(2021 개정)·Ta(2017 개정)가 다릅니다. 어느 쪽을 쓸지 정해야 합니다.
- 구간 표시: Li·Pb처럼 자연 변동이 큰 원소에서 지금의 "값 ± σ" 표시를 "자연 범위 구간" 표시로 바꿀지 정해야 합니다.
- 근거: [2차 04](docs/conformity-inspection-2026-10-02-r2/04-golden-abundance.md)

## 3. 공개와 책임

**⑥ 데이터 라이선스와 재배포 조건**
- `data/SOURCES.md`에 "공개 전 확인"으로 남아 있는 항목입니다.
- 지난번 푸시로 공개 저장소에 NNDC·CIAAW·KAERI·LARAWEB 페이지 사본이 증거 자료로 올라가 있습니다. 그대로 둘지 확인이 필요합니다.

**⑦ 사용 범위 고지**
- 예: "교육·참고용이며, 정밀 계측·의료 계산에는 평가 DB 원본을 사용할 것"
- 어디까지 책임질지는 개발자가 정할 일입니다.

**⑧ 운영 체계**
- 데이터 갱신 주기
- 갱신 책임자
- 변경 이력 공개 방식
- 사용자 오류 신고 창구

## 4. 외부 연락: 제가 하지 않은 일입니다

**⑨ 오류 보고 여부**
- NUBASE 평가자(AMDC)에 원문 오기 12건을 알릴지
- ENSDF/NNDC에 ⁶⁴Mnᵐ의 단위 오류를 알릴지. 채택값은 `440 ms`인데, 자체 주석의 측정값으로 계산하면 439 μs입니다.

**⑩ 실사용자 시험**
- 4~5명 모집, 과제 5개 진행
- 성공 기준 확정, 동의·보상 처리
- 시험 계획은 [1차 03 §5](docs/conformity-inspection-2026-10-02/03-verdict.md)에 있습니다.

## 5. 수정 착수 승인

**⑪ 어떤 수정부터 할지, 화면 표현을 어떻게 할지**
- 지금까지는 "코드 수정 금지"로 검증만 했습니다.
- 1순위(P0) 후보는 다음과 같습니다.
  - β⁺ 라벨을 "EC+β⁺"로 바꾸기
  - 전체 β 분기와 지연입자 분기를 계층으로 표시하기
  - `=?`와 `?` 구분 살리기
  - 이성질체 상태 문맥 바로잡기
  - 검색 오류 고치기
  - ¹⁶⁴Ho·¹⁸²Pt 정정
- 표현 방식은 교육 효과와 연구 정확성 사이에서 선택해야 합니다.
- 지연 글꼴 E2E 테스트를 어떻게 처리할지도 정해야 합니다. Pretendard가 로컬에 설치된 PC에서는 항상 실패하도록 전제가 잘못되어 있습니다.
