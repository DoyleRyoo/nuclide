# 04. 데이터

이 문서의 형식·통계는 2026-09-26에 원본 파일을 직접 내려받아 파싱해 확인한 값이다.

## 1. 원칙

1. **데이터는 앱에 내장한다** (d.md의 판단을 채택). 이유:
   - 평가본은 약 4년 주기로 나온다(AME/NUBASE 2003, 2012, 2016, 2020) → 실시간 조회가 필요 없다.
   - 크기가 작다: 시작할 때 받는 핵심 청크 gzip 약 170 KB, 나중에 받는 AME 상세 청크 약 255 KB (§10).
   - 서버·API가 없으니 운영 비용 0, 응답 지연 0, 오프라인 동작, 개인정보 문제 없음.
2. **원본은 고치지 않는다**. `data/raw/`에 받은 그대로 두고, 변환은 스크립트로만 한다.
3. **원문 문자열을 보존한다** (NFR-08). 표시할 값은 원문 문자열에서 만들고, 부동소수는 색상 계산·정렬에만 쓴다.
4. **변환 결과(JSON)도 저장소에 커밋한다**. 앱 빌드에 파이프라인이 필요 없고, CI는 다시 만든 결과가 커밋된 파일과 같은지 확인한다.

### 4.2 수치 파싱

- `#`는 값 끝에 붙는 **추정 표시**다(예: `28670#`, `1.8#`). `#`을 떼고 `est: true`로 표시한다.
- 빈 칸 → 값 없음. `*` → 계산 불가(AME 파일).
- 원문 문자열을 그대로 `v`에 보관하고, 계산용 수치는 따로 만든다.

### 4.3 상태 구분

| 종류 | 판별 | 앱에서 |
|---|---|---|
| 기저 상태 | `s` = 공백 (i = 0) | **차트의 칸** |
| 이성질체·준위 | `s` ∈ m, n, p, q, r, x | 칸에 딸린 들뜬 상태 목록 (패널에 표시, 반감기 없으면 "준위"로 표시) |
| IAS | `s` ∈ i, j | **제외** (186행) |

- 들뜬 상태의 표시 이름은 순서대로 m, m2, m3, m4, m5, m6 (NUBASE 문자 m, n, p, q, r, x에 대응). 예: ²³⁵U의 `n` 상태 → ²³⁵ᵐ²U, ID `U-235m2`.
- 들뜬 에너지 칸이 `non-exist`인 상태 16개(예: ⁷⁶Cuᵐ)는 보고됐지만 평가에서 존재하지 않는다고 본 상태다. 목록에는 남기고 `nonExistent: true`로 표시하며 들뜬 에너지는 비운다(§13).

## 5. 붕괴 모드 해석

### 5.1 문법

붕괴 필드는 `;`로 나뉜 항목의 목록이다. 항목 = `모드` + 관계 + 값 + 불확도.

| 관계 | 뜻 | 예 |
|---|---|---|
| `=` | 값(± 불확도) | `B-=100`, `A=99.99 1` |
| `~` | 근삿값 | `p~100` |
| `<` / `>` | 상한 / 하한 | `B-A<0.004` |
| `?` | 관측·예상되지만 세기 미상 | `B-n ?`, `2p ?` |
| `=?`, `= ?` | `?`와 같다 (실측: `B-=?`, `B+= ?`, `IT= ?`) | `B-=?;IT ?` |

`IS=`는 붕괴가 아니라 자연 존재비다. 목록에서 따로 떼어 `abundance`에 넣는다. 값 끝의 `#`(예: `A=3.310e-5#`)은 추정 표시로 떼고 `est: true`로 둔다.

### 5.2 토큰 → 범주 → 딸핵 변위

NUBASE2020 전체에 나오는 토큰은 아래가 전부다(실측). 표에 없는 토큰이 나오면 빌드를 실패시킨다.

| 범주 | 토큰 | 딸핵 (ΔZ, ΔN) |
|---|---|---|
| β− | `B-` | (+1, −1) |
| | `2B-` | (+2, −2) |
| | `B-n`, `B-2n`, `B-3n`, `B-4n` | (+1, −2), (+1, −3), (+1, −4), (+1, −5) |
| | `B-p`, `B-d`, `B-t` | (0, −1), (0, −2), (0, −3) |
| | `B-A` | (−1, −3) |
| | `B-SF` | 없음 (핵분열) |
| | `B` (부호 없음) | (+1, −1). ¹²⁶Pd의 p 상태(`B=72 8;IT=28 8`)에만 나온다. 중성자 과잉 핵이므로 β−로 읽고, 다른 곳에 나오면 빌드를 실패시킨다(§13) |
| β+/EC | `B+`, `EC`, `e+`, `EC+B+` | (−1, +1) |
| | `2B+` | (−2, +2) |
| | `B+p`, `B+2p`, `B+3p` | (−2, +1), (−3, +1), (−4, +1) |
| | `B+A` | (−3, −1) |
| | `B+pA` | (−4, −1) |
| | `B+SF` | 없음 (핵분열) |
| α | `A` | (−2, −2) |
| SF | `SF` | 없음 (핵분열) |
| p | `p`, `2p`, `3p` | (−1, 0), (−2, 0), (−3, 0) |
| n | `n`, `2n`, `3n` | (0, −1), (0, −2), (0, −3) |
| IT | `IT` | (0, 0) → 같은 핵종의 기저(또는 아래) 상태 |
| 클러스터 | `12C`, `14C`, `18O`, `20O`, `20Ne`, `22Ne`, `23F`, `24Ne`, `25Ne`, `28Mg`, `30Mg`, `32Si`, `34Si` | 방출 핵 (Zc, Nc)만큼 (−Zc, −Nc). 예: `14C` → (−6, −8) |
| | `24Ne+26Ne`, `28Mg+30Mg` | 여러 클러스터 합산 — 딸핵 없음 |
| 기타 | `d`, `3H`, `3He` | IAS 행에만 나오므로 앱에서는 쓰이지 않는다 |

딸핵은 (Z + ΔZ, N + ΔN)의 기저 상태로 연결한다. 데이터에 없으면 "데이터 없음"으로 표시한다.

### 5.3 주 붕괴 모드 판정 (칸 색)

1. 기저 상태 반감기가 `stbl`이면 **안정**.
2. 각 항목을 범주로 묶는다. β 지연 방출(`B-n`, `B+p` 등)은 부모 β 범주에 속한다.
3. 분기비 값이 **50% 이상**인 항목이 있으면, 그중 값이 가장 큰 항목의 범주.
4. 없으면 **첫 번째 항목**의 범주. NUBASE는 대체로 주 모드를 먼저 적고, 세기가 `?`인 첫 항목은 나머지 비율을 뜻하는 경우가 많다(예: `B+ ?;A=45.2 16` → β+ 약 55%).
5. 항목이 하나도 없으면 **미상**. (NUBASE2020 기저 상태에는 해당 없음)

첫 항목 규칙만 쓰면 틀리는 실제 사례 4건 — 골든 테스트로 고정한다:

| 핵종 | 원문 | 판정 |
|---|---|---|
| ⁷³Rb | `B+ ?; p~100` | p |
| ¹⁷⁷Au | `A=40 6;B+=60 6` | β+/EC |
| ²³³Cm | `A=20 10;B+=80 10` | β+/EC |
| ²⁷¹Sg | `A=42 23;SF=58 23` | SF |

## 6. AME2020 형식과 결합

### 6.1 mass_1.mas20.txt

- Fortran 형식: `a1,i3,i5,i5,i5,1x,a3,a4,1x,f14.6,f12.6,f13.5,1x,f10.5,1x,a2,f13.5,f11.5,1x,i3,1x,f13.6,f12.6`
- 데이터는 `micro-u`가 들어 있는 머리줄(36번째 줄) 다음, 37번째 줄부터 시작한다.

| 열 | 항목 |
|---|---|
| 1 | 제어 문자 |
| 2–4 | N − Z |
| 5–9 | N |
| 10–14 | Z |
| 15–19 | A |
| 21–23 | 원소 기호 |
| 24–27 | 출처 표시 |
| 29–42 / 43–54 | 질량 초과 / 불확도 (keV) |
| 55–67 / 69–78 | 핵자당 결합에너지 / 불확도 (keV) |
| 80–81 | `B-` 라벨 |
| 82–94 / 95–105 | β− 붕괴 에너지 / 불확도 (keV) |
| 107–109 + 111–123 / 124–135 | 원자 질량 정수부 + 소수부(μu) / 불확도(μu). 예: `235` + `043928.117` → 235 043 928.117 μu |

### 6.2 rct1.mas20.txt, rct2_1.mas20.txt

- Fortran 형식: `a1,i3,1x,a3,i3,1x,6(f12.4,f10.4)` → A = 2–4열, 원소 = 6–8열, Z = 9–11열, 이어서 (값 12자 + 불확도 10자) × 6쌍. k번째 쌍(0부터)의 값은 13 + 22k열부터 12자, 불확도는 25 + 22k열부터 10자.
- rct1의 6쌍: S(2n), S(2p), Q(α), Q(2β−), Q(εp), Q(β−n)
- rct2_1의 6쌍: S(n), S(p), Q(4β−), Q(d,α), Q(p,α), Q(n,α)
- 머리줄(`1 A  elt  Z ...`)은 파일마다 한 번. 데이터 줄은 정규식으로 판별한다.

### 6.3 공통 규칙

- `#`는 소수점 자리에 들어간 추정 표시다(AME 머리 설명). 이번 파일들에서는 모두 정수부 끝에 붙어 있다(예: `-13717#`). `#`을 떼고 `est: true`.
- `*` = 계산 불가 → 값 없음.
- 파일 1–3은 **반올림하지 않은** 값이다(AME 머리 설명). 표시할 때 §9의 반올림 규칙을 쓴다.
- 결합 키는 (Z, A). NUBASE 기저 상태 3,558개와 1:1이어야 한다(검증).
- QEC는 파일에 없으므로 계산한다: `QEC(Z, A) = −Qβ−(Z−1, A)` (mass_1의 β− 붕괴 에너지, 불확도도 그대로). `Qβ+ = QEC − 1,021.998 keV` (2mₑc²).

## 7. 출력 스키마

`src/data/types.ts`에 정의하고, 빌드 스크립트와 앱이 함께 쓴다.

```ts
/** 원문 문자열을 보존하는 측정값 */
export interface Measured {
  v: string;              // 원문 값 (예: "5.70", "7e-9", "28670")
  u?: string;             // 원문 불확도 (예: "0.03", "6", "+18-8", ">620ns")
  est?: true;             // '#' 계통성 추정
  rel?: '<' | '>' | '~';  // 한계·근사
}

export type DecayCategory =
  | 'stable' | 'beta-' | 'beta+' | 'alpha' | 'sf' | 'p' | 'n'
  | 'it' | 'cluster' | 'other' | 'unknown';

export interface DecayBranch {
  mode: string;                         // NUBASE 토큰 원문 ("B-n", "EC", "14C")
  cat: DecayCategory;
  rel: '=' | '~' | '<' | '>' | '?';
  value?: string;                       // 분기비(%) 원문
  unc?: string;                         // 분기비 불확도 원문
  est?: true;                           // 값 끝 '#' 추정
  pct?: number;                         // 정렬·판정용 수치 (없으면 '?')
  daughter?: { dz: number; dn: number };// 딸핵 변위 (SF 등은 없음)
  note?: string;                        // "[gs=0,m=100]" 같은 부가 정보
}

export interface HalfLife {
  kind: 'value' | 'stable' | 'unknown' | 'particle-unbound';
  value?: string;                       // 원문 ("5.70")
  unit?: string;                        // 원문 ("ky")
  unc?: string;                         // 원문 ("0.03" 또는 ">620ns")
  est?: true;
  rel?: '<' | '>' | '~';
  seconds?: number;                     // 색상·정렬용
}

export interface NuclearState {
  id: string;                           // "U-235", "U-235m", "Hf-178m2"
  level: number;                        // 0 = 기저, 1–6 = m, m2 … m6
  exc?: Measured;                       // 들뜬 에너지 (keV)
  massExcess?: Measured;                // keV
  halfLife: HalfLife;
  jpi?: string;                         // 원문 ("7/2-*", "(3/2+)", "2-#")
  decays: DecayBranch[];                // 원문 순서
  abundance?: Measured;                 // IS (%)
  discovery?: number;                   // 발견 연도
  orderUncertain?: true;                // 68열 '*'
  orderInverted?: true;                 // 69열 '&'
  nonExistent?: true;                   // 들뜬 에너지 칸 'non-exist' (§4.3)
}

export interface Nuclide extends NuclearState {  // 기저 상태 = 차트의 칸
  z: number;
  n: number;
  a: number;
  symbol: string;                       // "U", 중성자는 "n"
  primary: DecayCategory;               // 칸 색 (§5.3)
  observed: boolean;                    // 발견 연도 유무
  naturalRadioactive: boolean;          // 자연 존재 띠 표식 조건
  excited: NuclearState[];              // IAS 제외, 에너지 순
  ame?: {                               // P1
    bindingPerA?: Measured;             // keV
    atomicMass?: Measured;              // μu
    qBetaMinus?: Measured; qEC?: Measured; qAlpha?: Measured;
    q2BetaMinus?: Measured; qECp?: Measured; qBetaMinusN?: Measured;
    sn?: Measured; sp?: Measured; s2n?: Measured; s2p?: Measured;
  };
}

export interface NuclideDataset {
  schemaVersion: 1;
  meta: {
    sources: { name: string; file: string; sha256: string }[];
    counts: Record<string, number>;
    bounds: { zMin: number; zMax: number; nMin: number; nMax: number };
  };
  nuclides: Nuclide[];                  // Z, 그다음 N 오름차순
}
```

- 위 타입은 **앱 안의 모델**이다. 파일에는 원본에서 온 값만 저장하고, 표로 계산할 수 있는 값은 `src/data/hydrate.ts`가 로드할 때 채운다. 크기 예산(§10) 때문이다.
  - 저장하지 않는 값: `id`, 기저 상태의 `level`, `n`, `symbol`, `observed`, `primary`, `naturalRadioactive`, `HalfLife.seconds`, `DecayBranch`의 `cat`·`pct`·`daughter`, AME `qEC`(§6.3).
  - 저장 형식 타입: `StoredDataset`/`StoredNuclide`/`StoredState`(`nuclides.json`), `AmeDetailFile`(`ame.json`). `ame.json`은 핵종 순서대로 한 행씩, 값은 `"v u"`(추정값 `"v# u"`) 문자열이다.
  - 붕괴 토큰 표(`DECAY_MODES`), 단위 표(`UNIT_SECONDS`), 주 모드 판정(`primaryCategory`)은 `src/data/decay.ts` 하나를 빌드와 앱이 같이 쓴다. 빌드 검증(§11)도 hydrate한 결과에 대해 돌므로 검증한 모델과 앱이 보는 모델이 같다.
- 출력은 결정적(deterministic)이어야 한다: 키 순서 고정, 생성 시각을 넣지 않는다(원본 파일 해시만 기록). 핵종 하나를 한 줄로 써서 diff를 읽을 수 있게 한다.
- 앱은 로드 후 실행용 색인을 만든다: `grid: Int16Array(119 × 178)`(칸 → 핵종 인덱스, 없으면 −1), `byId: Map`, 행별 N 범위, 범주별 개수, 검색 색인.

## 10. 빌드 파이프라인

```
data/raw/*.txt (원본, 수정 금지)
      │
      ▼  npm run data:build  (scripts/build-data/, tsx로 실행)
  ① NUBASE 파싱 → ② IAS 제외, (Z, A)로 기저·들뜬 상태 묶기 → ③ 붕괴 모드 해석(토큰 검사)
  ④ AME 3개 파일 파싱 → (Z, A)로 결합 → ⑤ 저장 형식 두 개 생성
  ⑥ hydrate + AME 결합(범주·딸핵·QEC 계산) → 검증(§11) → ⑦ 결정적 JSON 출력
      │
      ▼
src/data/generated/nuclides.json  핵심: NUBASE + AME 핵자당 결합에너지 (gzip 169 KB)
src/data/generated/ame.json       AME 상세: 원자 질량, Q값, 분리 에너지 (gzip 255 KB)
      │   (둘 다 저장소에 커밋)
      ▼  앱에서 동적 import() → Vite가 해시 파일명의 별도 청크(nuclides-*.js, ame-*.js)로 분리
브라우저: 앱 껍데기 → nuclides 청크 로드 후 차트 표시 → ame 청크를 뒤이어 받아 패널 값 채움
          (PWA가 둘 다 미리 캐시)
```

- 청크를 나눈 이유: 반올림 전 AME 값(12개 × 3,558 핵종)은 숫자가 거의 무작위라 gzip이 잘 안 된다. 한 파일로 두면 gzip 603 KB로 시작 데이터 예산(NFR-03, 250 KB)을 넘는다. 색상 모드에 필요한 핵자당 결합에너지만 핵심 청크에 두고, 패널에서만 쓰는 나머지 AME 값은 첫 차트 뒤에 받는다([ADR-14](06-roadmap.md#4-결정-기록-adr)). AME 값을 미리 반올림해 줄이는 방법은 원문 보존 원칙(§1) 때문에 쓰지 않았다.
- `npm run data:check`: 다시 만든 결과가 커밋된 두 JSON과 다르면 실패 (CI에서 실행).
- 변환 요약(행 수, 범주별 개수, 파일 크기·gzip 크기, 경고)을 콘솔에 출력한다.
- 원본의 바이트를 보존하도록 `.gitattributes`에서 `data/raw/**`의 줄 끝 변환을 끈다(`rct1.mas20.txt`만 원래 CRLF).

## 12. 데이터 갱신 절차

1. AMDC에서 새 평가본을 받아 `data/raw/`를 교체하고 `data/SOURCES.md`를 고친다.
2. 파일 머리의 형식 정의를 이전 판과 비교해, 바뀌었으면 파서를 고친다.
3. `npm run data:build` → 검증 실패 항목(개수 스냅샷 등)을 검토해 스냅샷을 새 값으로 갱신한다.
4. 바뀐 핵종 수와 주요 변화를 커밋 메시지에 남긴다.
5. 앱 버전을 올려 배포한다. PWA 사용자는 다음 방문 때 자동으로 갱신된다.

## 13. 알려진 원본 특이사항

앱은 원본 값을 임의로 고치지 않는다. 이상해 보이는 값은 여기에 기록만 한다.

| 항목 | 내용 |
|---|---|
