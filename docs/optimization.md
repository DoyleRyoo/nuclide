분석을 마쳤습니다. 코드는 바꾸지 않았고, 코드를 읽고 이미 기록된 측정값(`docs/performance-2026-09-27.json`)을 근거로 정리했습니다.

## 먼저 알아둘 점: 병목은 JS 계산 밖에 있습니다

60fps에 못 미치는 구간은 LOD 1 이동 하나(평균 55.9 FPS)입니다. 그런데 이 구간에서도 엔진이 한 프레임을 계산하는 시간은 중앙값 6.5 ms, p95 8.7 ms로 16.7 ms 예산 안에 있습니다. 그런데도 프레임 간격 p95가 33.3 ms이므로, 시간은 **JS가 끝난 뒤 브라우저가 글자와 도형을 픽셀로 그리는 단계(래스터화·합성)**에서 쓰이고 있을 가능성이 큽니다. LOD 1은 한 프레임에 글자를 약 2,037번 그려서 모든 단계 중 가장 많습니다.

또 이 수치는 GPU 없이 소프트웨어로 그렸을 수 있는 headless Chromium, 픽셀 밀도(DPR) 1 환경에서 잰 값입니다. 그래서 최적화보다 **측정 환경을 먼저 바로잡는 것**이 첫 단계입니다.

## 권장 순서

| 순서 | 할 일 | 기대 효과 | 난이도 |
|---|---|---|---|
| 1 | 실제 GPU 환경에서 다시 측정 | 진짜 병목 확인 | 낮음 |
| 2 | LOD 1 글자를 글꼴·색별로 묶어 그리기 | LOD 1 개선 (핵심 후보) | 낮음 |
| 3 | 줌할 때 React 전체가 다시 그려지는 문제 없애기 | 줌 중 끊김 감소 | 낮음 |
| 4 | 선택 링의 그림자 효과를 미리 그려 두기 | 선택 상태에서 이동할 때 개선 | 낮음 |
| 5 | 작은 칸의 도형 단순화 | 소폭 개선 | 낮음 |
| 6 | 글자 이미지 캐시 | 글자 비용을 크게 절감 | 중간 |
| 7 | 이동 중 이전 화면 재사용(타일·블릿) | 모든 LOD의 이동이 빨라짐 (가장 큼) | 높음 |

1–5는 작업이 작고, 6–7은 1–5를 한 뒤에도 모바일이나 고해상도 화면에서 모자랄 때만 하는 것을 권합니다.

## 항목별 설명

**1. 측정 환경 바로잡기**
- 헤드리스가 아닌 실제 Chrome에서 DevTools Performance 패널로 기록합니다. JS 외에 Paint·Rasterize·GPU 작업이 얼마나 걸리는지 봐야 합니다.
- 고해상도 화면(DPR 2) 조건도 재야 합니다. 그리는 픽셀이 4배라 글자 비용이 커지고, MacBook·휴대폰이 이 조건입니다.
- 중급 모바일은 CPU 속도 제한(4×)이나 실기기로 확인합니다.

**2. LOD 1 글자 묶어 그리기**
- [labels.ts:125](src/chart/render/labels.ts#L125)의 `drawName`은 칸마다 질량수(굵기 600)와 원소 기호(굵기 700)를 번갈아 그립니다. 그래서 한 프레임에 `ctx.font`가 약 1,900번 바뀝니다. 글꼴 문자열 해석은 비싼 작업입니다.
- 칸마다 글자색(`fillStyle`)과 투명도(`globalAlpha`)도 바뀝니다.
- 개선 방법:
  - 모든 칸의 질량수를 먼저 그리고, 그다음 원소 기호를 그립니다. 글꼴 변경이 프레임당 2번 정도로 줄어듭니다.
  - [cells.ts](src/chart/render/cells.ts)가 이미 만들어 둔 "색 인덱스별 정렬 순서"를 재사용하면 색 변경도 팔레트 개수 이하로 줄어듭니다.
  - 이동 중에는 배율이 그대로라 칸마다 하는 글자 폭 계산도 한 번만 해 두고 재사용할 수 있습니다.

**3. 줌할 때 React 다시 그리기 줄이기**
- [App.tsx:169](src/app/App.tsx#L169)에서 카메라가 바뀔 때마다 `setScale(c.s)`를 호출합니다. 그래서 줌하는 동안 **매 프레임 App 전체가 다시 그려집니다**.
- 다시 그릴 때마다 비용도 큽니다.
  - [App.tsx:53](src/app/App.tsx#L53)은 스토어 전체를 구독합니다.
  - 범례 개수는 3,558개 핵종을 7번 훑어 계산합니다([App.tsx:552](src/app/App.tsx#L552)).
  - 보이는 핵종 수도 매번 다시 셉니다([App.tsx:321](src/app/App.tsx#L321)).
  - 정보 패널도 함께 다시 그려집니다.
- 개선 방법:
  - 실제로 쓰는 값은 "256 이상인가(확대 버튼 비활성)"와 "64 미만인가(툴팁 표시)"뿐입니다. 이 두 값만 상태로 두면 경계를 넘을 때만 다시 그립니다.
  - 스토어는 필요한 값만 골라 구독하고, 범례 개수는 메모이제이션합니다.
  - 정보 패널·검색창·미니맵은 `React.memo`로 감쌉니다.
  - 호버 툴팁은 작은 별도 컴포넌트로 분리합니다.

**4. 선택 링 그림자**
- [overlay.ts:104](src/chart/render/overlay.ts#L104)의 `shadowBlur = 12`는 가우시안 블러라 비쌉니다. 핵종을 선택한 채로 이동하면 매 프레임 다시 계산됩니다.
- 기존 성능 측정은 아무것도 선택하지 않은 상태라 이 비용이 수치에 빠져 있습니다.
- 크기별로 한 번 미리 그려 두고 이미지로 붙이면 됩니다.

**5. 도형 단순화**
- LOD 1의 둥근 모서리는 반지름이 2–4px라 눈에 거의 띄지 않습니다([cells.ts:84](src/chart/render/cells.ts#L84)). 일정 크기 미만에서는 일반 사각형으로 그려도 됩니다.
- 라이트 테마는 모든 칸의 테두리를 한 번 더 그립니다([cells.ts:76](src/chart/render/cells.ts#L76)). 칸 사이 간격의 배경색으로 대신할 수 있는지 검토할 만합니다.

**6. 글자 이미지 캐시**
- 핵종별 이름표를 배율 구간마다 한 번 오프스크린 캔버스에 그려 두고, `fillText` 대신 `drawImage`로 붙입니다.
- 이동 중에는 배율이 변하지 않아 매번 캐시를 그대로 씁니다.
- 테마·색상 모드가 바뀌거나 웹 글꼴이 로드되면 캐시를 버려야 합니다.

**7. 이동 중 이전 화면 재사용**
- 이동만 할 때는 화면 내용이 평행이동될 뿐입니다. 방법은 두 가지입니다.
  - 이전 프레임을 옮겨 복사하고, 새로 드러난 가장자리만 그립니다.
  - 현재 배율로 타일 캐시를 만들어 붙입니다.
- 줌하는 동안에는 캐시를 늘려 보여 주고, 줌이 끝나면 선명하게 다시 그리는 지도 앱 방식을 쓸 수 있습니다.
- 효과는 가장 크지만 복잡하고, 무효화 조건(테마, 색상 모드, 범례 강조, 예측 핵종 표시, 창 크기, DPR)을 모두 챙겨야 합니다.

## 지금은 하지 않아도 되는 것

- **데이터 로딩**: 파싱과 색인을 합쳐 33–45 ms로 50 ms 예산 안이고, 번들도 예산 안입니다. 모바일에서 100 ms를 넘을 때만 Web Worker로 옮기는 것을 검토하면 됩니다.
- **검색**: 핵종 3,558개 규모라 부담이 작습니다. 반응 속도(NFR-02)를 재 보고 문제가 있을 때만 손대면 됩니다.
- **WebGL 전환**: ADR-02에 적힌 대로, 1–7을 한 뒤에도 모바일에서 30fps를 못 넘을 때만 검토합니다.
