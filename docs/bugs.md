# 사용자 불편 사항 (버그 목록)

기준일: 2026-09-30 · 코드 기준: `43555f9`

사용자가 겪은 불편 사항을 정리한다. 항목마다 증상, 재현 방법, 기대 동작, 원인 코드, 수정 방향, 완료 기준을 적는다. 2026-09-30 코드 검토와 브라우저 실측 결과를 반영했다. 제품 코드는 아직 수정하지 않았으며, 아래 상태는 구현 상태를 뜻한다. 수치 중 "추정"은 미검증 값이고, "실측"은 명시한 환경에서의 값이므로 대상 기기에서도 확인해야 한다.

## 검증 결과와 적용 조건

- 현재 코드의 원인 진단과 실측 기반 눈금자 폭, 두 칸 정렬, 청록색 제거, 패널 글자 확대 방향은 타당하다. 다만 기존 제안의 가로 화면 누락, 상자 여백·간격 계산, 확대 접근성 대안, 테스트 범위를 보완했다.
- Windows Chrome에서 앱의 웹 글꼴 로드 후 실제 차트 캔버스를 측정했다. 모바일 10px 글꼴의 `118 Og`는 약 34.5px, `100 Fm`은 약 35.3px로 가용 폭 30px를 넘었다. 숫자는 앱의 `tabular-nums`가 적용된 상태에서 같은 자릿수끼리 폭이 같았다. 별도 캔버스에서 얻은 비례 숫자 폭은 근거로 쓰지 않는다.
- 기존 `max-width: 767px` 안에만 16px 규칙을 임시 적용한 결과, 폭 768·844·932px에서는 검색 입력과 `select`가 13px로 남았다. 이는 CSS 적용 누락의 확인이며 iPhone 자동 확대를 실기기로 재현한 결과는 아니다.
- 현재 코드 기준 단위 테스트 69개와 빌드가 통과했다. 설치된 Chrome에 Pixel 7 에뮬레이션을 적용한 기존 지도 E2E는 7개 통과, 데스크톱 전용 2개 제외였다. 제안 전체를 구현한 뒤의 통과 결과는 아니다.
- iPhone Safari의 입력 자동 확대·노치, Android 실기기 제스처는 아직 검증하지 않았다. 아래 완료 기준을 충족하기 전에는 해결 완료로 바꾸지 않는다.

2. **묶음 B (2–5번)**: [rulers.ts](../src/chart/render/rulers.ts)의 Z·N 눈금자와 [lod.ts](../src/chart/lod.ts)의 표시 간격을 함께 고친다. 눈금자 폭, 두 칸 배치, 상자 안팎 여백, 선택·호버 충돌 처리를 하나의 계산 규칙으로 묶는다. 7번의 캔버스 눈금자 글자 크기도 이때 함께 올린다.
3. **묶음 C (6–7번)**: CSS에 글자 크기 토큰을 만들고 한 번에 올린다. 정보 패널 머리글(6번)은 토큰보다 한 단계 크게 따로 정한다.

## 1. iOS에서 검색하면 검색창·메뉴까지 확대된다

**증상**
- iPhone Safari에서 검색창을 누르면 지도뿐 아니라 검색창, 메뉴 버튼, 범례 등 화면 전체가 확대된다.
- 검색 결과를 고른 뒤에도 확대가 풀리지 않는다. 사용자가 두 손가락으로 직접 축소해야 원래대로 돌아온다.

**재현**
1. iPhone Safari에서 앱을 연다(세로 화면).
2. 위쪽 검색창을 누른다. 키보드가 올라오면서 화면이 확대된다.
3. `U-235`를 입력하고 결과를 고른다. 화면은 확대된 채로 남는다.
4. 메뉴(≡) → 설정 창의 드롭다운(색상 모드·테마·휠)에서도 확인한다.
5. 가로로 회전해 폭 768px 이상에서도 검색창과 상단 도구 모음·설정 창의 `select`를 확인한다. 회전으로 적용되는 레이아웃이 달라진다.

**기대 동작**
- 검색창과 설정에 포커스하거나 지도 줌을 조작할 때 UI가 의도치 않게 확대되지 않는다.
- 지도 확대·축소는 캔버스에만 적용한다. 사용자가 글자를 읽기 위해 직접 실행하는 UI 확대는 보장한다.
- UI 핀치를 차단하는 단계에서는 7번의 100–200% 글자 크기 설정으로 같은 접근성 요구를 충족한다. 이 대안의 검증 전에는 기존 UI 핀치를 유지한다.

**원인**
- **입력창 자동 확대**: iOS Safari는 작은 글꼴의 입력 요소에 포커스할 때 페이지를 자동 확대할 수 있다. 검색 입력과 `select`의 계산된 글꼴 크기를 16px 이상으로 확보하고 실기기에서 확인한다.
  - 검색 입력은 13px이고 모바일에서는 12px이다([global.css:191](../src/styles/global.css#L191), [global.css:974](../src/styles/global.css#L974)).
  - 설정 창의 `select`도 13px이다([global.css:251](../src/styles/global.css#L251)).
  - 보고된 증상에서는 포커스가 빠진 뒤에도 확대가 남는다. 핵종 검색 결과를 고르면 포커스를 지도로 옮기는 코드([App.tsx:301](../src/app/App.tsx#L301))는 있지만 페이지 확대 배율을 복원하는 코드는 없다.
- **UI 위 핀치 확대**: 일반 UI 전체에 적용되는 확대 차단은 없다.
  - 지도 입력 영역에는 `.chart { touch-action: none }`이 걸려 있다([global.css:116](../src/styles/global.css#L116)). 미니맵과 시트 손잡이에도 개별 `none` 규칙이 있지만 검색·설정·패널 본문 전체를 차단하는 규칙은 아니다.
  - Safari 제스처 이벤트 차단도 캔버스에만 붙어 있다([safariGesture.ts:25](../src/chart/input/safariGesture.ts#L25)).
  - 그래서 UI 위의 페이지 핀치는 허용되어 있다. 이것은 설계 문서 [02 §11](02-ux-interaction.md#11-터치-제스처)의 "패널과 UI 영역은 기본 동작을 유지한다(페이지 확대 가능 → 접근성)"대로 만든 동작이다. 입력창 자동 확대와는 다른 문제이며, 차단하려면 기존 접근성 요구를 충족할 대안과 설계 변경이 필요하다.

**수정 방향**
1. **입력 요소 글자를 16px 이상으로** 한다. 이것이 핵심 수정이다.
   - `.search-box input`과 `select`의 기본 규칙을 16px 이상으로 바꾸고, 모바일의 12px 재정의를 제거하거나 같은 토큰으로 바꾼다. `max-width: 767px`에만 적용하지 않는다. 데스크톱·태블릿·iPhone 가로 화면도 같은 최솟값을 보장한다.
   - 7번의 일괄 글자 크기 변환보다 이 규칙을 우선한다. 글자 크기 설정 100%에서도 16px 미만으로 내려가면 안 된다.
   - 16px이면 모바일 검색창에 placeholder `핵종 검색 — U-235, 우라늄, 99mTc`가 다 들어가지 않는다(폭 360px 화면에서 입력 칸은 약 200px, 추정).
   - 공간을 확보하려면 좁은 화면에서 `/` 단축키 표시(`<kbd>`, [SearchBox.tsx:86](../src/components/SearchBox.tsx#L86))를 숨긴다. 실제 키보드 단축키는 유지한다. 필요하면 모바일용 placeholder를 짧게 만든다.
2. **UI 영역의 핀치 차단은 200% 확대 대안 검증 후 적용한다.**
   - [01 NFR-05](01-requirements.md#6-비기능-요구사항)와 [03 §11](03-visual-design.md#11-접근성-점검표)의 접근성 요구를 유지한다. 7번의 기본 글자 크기 인상만으로는 확대 대안이 되지 않는다.
   - 대안을 제공하지 않는 단계에서는 `html`과 `document`에 전역 확대 차단을 추가하지 않는다. 기존 UI 핀치를 유지한 상태로 입력 자동 확대 방지를 먼저 검증한다.
   - 대안을 검증한 뒤 차단한다면 `html`에 `touch-action: pan-x pan-y`를 적용한다. 캔버스는 지금처럼 `none`을 유지하고, 정보 패널과 범례의 세로 스크롤은 계속 허용한다.
   - Safari 실기기에서 CSS만으로 부족한 경우 전역 `gesturestart` 취소를 보완책으로 검증한다. 리스너는 `{ passive: false }`로 등록하고 해제 함수도 둔다. 전파를 중단하지 않아 [safariGesture.ts](../src/chart/input/safariGesture.ts)의 지도 줌 처리와 충돌하지 않게 한다. "JS 한 줄"만으로 완료로 보지 않는다.
3. **viewport 메타에 `maximum-scale=1`은 넣지 않는다.**
   - 브라우저별 viewport 확대 제한 동작에 기대어 입력 자동 확대를 고치지 않는다. 입력 글꼴 수정과 사용자 확대 대안으로 해결한다.
4. **설계 문서를 고친다.**
   - [02 §11](02-ux-interaction.md#11-터치-제스처)에 자동 확대 방지와 의도한 확대 보장, UI 핀치 차단의 선행 조건을 구분해 적는다.
   - [06 결정 기록](06-roadmap.md#4-결정-기록-adr)에 실제로 구현·검증한 확대 방식과 제스처 처리 범위를 ADR로 남긴다. 200% 확대 요구를 완화하지 않는다.

**완료 기준**
- iPhone Safari 실기기에서 기본 페이지 배율 100%로 시작해 검색창 누르기 → 입력 → 결과 고르기까지 `window.visualViewport.scale`이 1로 유지된다. 사용자가 먼저 확대한 경우에는 1로 강제 복원하지 않고 포커스 전 배율을 유지한다.
- 세로·가로 화면 모두 검색 입력과 상단 도구 모음·설정 창 드롭다운에 포커스해도 의도치 않은 확대가 없다. 지원 버전은 [01 NFR-04](01-requirements.md#6-비기능-요구사항)의 최신 2개 메이저 버전을 따른다.
- 지도 위 핀치는 지도만 확대한다. UI 핀치를 유지하는 단계에서는 사용자 페이지 확대가 가능하고, 차단하는 단계에서는 헤더·범례·패널 위 핀치가 차단되면서 7번의 대안이 200% 확대를 제공한다.
- 정보 패널(하단 시트)과 펼친 범례의 세로 스크롤이 정상 동작한다.
- 회귀 테스트: 폭 360·390·430px 세로, 844·932px 가로, 경계 767·768px에서 검색 입력과 각 화면에 표시되는 모든 `select`의 계산된 글자 크기가 16px 이상인지 검사한다. 설정 창도 열어 확인한다.
  - Playwright WebKit의 모바일 에뮬레이션은 iPhone Safari 실기기 검증을 대체하지 않는다. 자동 테스트의 CSS 조건 통과와 실기기의 자동 확대 방지 통과를 별도로 기록한다.

## 2. 모바일에서 왼쪽 원자번호 열이 잘린다

**증상**
- 폭 768px 미만 화면에서 Z 눈금자 라벨의 왼쪽이 잘린다.
  - 세 자리 번호(`100 Fm` ~ `118 Og`)에서 확실히 잘린다.
  - 두 자리 번호인 `96 Cm`도 10px에서 약 30.5px로 실측되어 가용 폭 30px를 넘었다. 다른 기호도 전체 목록을 측정해 확인한다.
- 선택한 원소의 강조 알약보다 글자가 더 넓어서 글자가 알약 밖으로 삐져나온다.
- iPhone 가로 화면에서는 눈금자가 통째로 노치(센서 영역) 밑에 가려질 수 있다.

**재현**
1. 390×844 모바일 화면(또는 DevTools 모바일 에뮬레이션)에서 앱을 연다.
2. 지도를 오른쪽 위(무거운 원소 쪽)로 옮겨 Z 100 이상 라벨을 본다. 앞자리가 잘려 보인다.
3. `Og-294`를 검색해 선택한다. 알약 밖으로 글자가 나온다.

**기대 동작**: Z 0–118의 모든 라벨이 잘리지 않고, 화면 왼쪽 가장자리와 여백을 둔다.

**원인**
- 모바일 눈금자 폭은 36px 고정이다([rulers.ts:9](../src/chart/render/rulers.ts#L9)).
- 라벨은 오른쪽 끝에서 6px 안쪽인 x = 30px에 오른쪽 정렬로 그린다([rulers.ts:73](../src/chart/render/rulers.ts#L73)). 쓸 수 있는 폭은 30px이다.
- 실제 차트 캔버스에서 `118 Og`는 10px 글꼴로 약 34.5px, `100 Fm`은 약 35.3px였다. 모바일에서는 왼쪽 약 4.5px·5.3px가 캔버스 밖으로 나간다(Windows Chrome, 웹 글꼴 로드 후 실측).
- 데스크톱의 가용 폭은 42px이다. 12px 글꼴의 `118 Og`는 약 41.4px지만 `100 Fm`은 약 42.4px여서 데스크톱도 전체 라벨을 검사해야 한다. 이 값은 해당 측정 환경의 결과이며 기기별 재확인이 필요하다.
- `viewport-fit=cover`([index.html:5](../index.html#L5)) 때문에 가로 화면에서 캔버스가 노치 밑까지 깔린다. 그런데 `safe-area-inset-left`를 반영하는 코드가 없다. 지금은 위쪽([global.css:957](../src/styles/global.css#L957))과 패널 아래쪽([global.css:1057](../src/styles/global.css#L1057))만 반영한다.

**수정 방향**: 보고에 적힌 "왼쪽 패딩" 해법을 구체화한다.
1. **안전 영역과 상자 안팎 여백을 구분한다.**
   - 노치 안전 영역 `s = max(0, safe-area-inset-left)`는 라벨과 알약 왼쪽 바깥에 확보한다. 알약 바깥 여백 `m = 2px`, 알약 안쪽 여백 `p = max(6px, 글자 크기 × 0.5)`는 별도 값이다.
   - JS에서는 `:root { --safe-left: env(safe-area-inset-left, 0px) }`의 계산된 값을 `getComputedStyle`로 읽어 엔진에 넘긴다.
   - 크기 변경·회전 시 안전 영역을 다시 읽고 최종 폭을 재계산한다. 안전 영역이 바뀌었다는 이유로 글자 폭까지 다시 측정할 필요는 없다.
2. **폭을 두 칸의 실측 폭과 상자 여백으로 정한다.**
   - `f`는 최종 글자 크기, `a`는 번호 칸의 최대 폭, `b`는 기호 칸의 최대 폭, `g = f × 0.3`은 두 칸 사이 간격이다. 3번의 측정 규칙을 따른다.
   - 콘텐츠 폭 `c = a + g + b`, 알약 시작점 `x = s + m`, 알약 폭 `w = c + 2p`, 눈금자 폭 `rw = ceil(s + 2m + 2p + c)`로 통일한다. 정수 올림으로 생기는 1px 미만의 여유는 눈금자 오른쪽 바깥에 남긴다.
   - 예를 들어 `f = 12`, `s = 0`, `a = 23`, `b = 20`이면 `g = 3.6`, `p = 6`, `c = 46.6`, `x = 2`, `w = 58.6`, `rw = 63px`다. 이는 계산 예이며 고정 구현값이 아니다. 두 칸의 예약 영역과 알약 사이에는 좌우 6px가 확보된다.
   - 종전의 "왼쪽 여백 4px, 알약은 2px 안쪽"만으로는 내부 여백이 2px라서 최소 6px 조건을 만족하지 못한다. 위 공식을 2·3·4번에서 공통으로 사용한다.
   - 글꼴 크기·패밀리·굵기·숫자 폭 설정이 바뀌면 재측정한다. 웹 글꼴 로드 후에는 [TextCache.clear](../src/chart/render/text.ts#L63)로 이전 측정값을 버리고 다시 측정한다. 기존 [글꼴 로드 콜백](../src/chart/ChartEngine.ts#L163)도 새 폭 계산을 호출하도록 연결한다.
3. **눈금자 폭을 따로 적어 둔 곳을 함께 고친다.** 지금은 폭 값이 여러 곳에 흩어져 있다.

   | 위치 | 현재 값 |
   |---|---|
   | [rulers.ts:8](../src/chart/render/rulers.ts#L8) `rulerSize` | 36 / 48. 엔진의 눈금자 클릭 판정([ChartEngine.ts:492](../src/chart/ChartEngine.ts#L492))도 이 함수를 쓴다 |
   | [App.tsx:238](../src/app/App.tsx#L238) `setSafeInsets` | `left: mobile ? 36 : 48` |
   | [global.css:313](../src/styles/global.css#L313), [:369](../src/styles/global.css#L369) (`.map-meta`, `.legend`) | 데스크톱 68px / 64px |
   | [global.css:987](../src/styles/global.css#L987), [:999](../src/styles/global.css#L999) (모바일 `.map-meta`, `.legend`) | 46px (= 36 + 10) |
   | [global.css:126](../src/styles/global.css#L126) (`.app-header`) | 데스크톱 68px |

   엔진의 최종 `rw`를 CSS 변수 `--ruler-w`로 내보내고, CSS는 `calc(var(--ruler-w) + 간격)`으로 쓴다. 렌더링·클리핑·클릭 판정·`setSafeInsets`도 같은 값을 사용한다. 초기 로드, 웹 글꼴 로드, 화면 회전, 7번의 글자 크기 설정 변경 모두에서 함께 갱신한다. 모바일 헤더는 기존 한 줄 배치를 유지하되 노치 안전 영역과 겹치지 않는지도 확인한다.
4. **문서를 고친다.** [03 §6.4](03-visual-design.md#64-눈금자)의 폭 값, [02 §1.1](02-ux-interaction.md#11-데스크톱-폭--1200px)의 "폭 48px", [02 §1.3](02-ux-interaction.md#13-모바일--768px)의 "Z 폭 36px"를 바꾼다.

**함께 확인할 것 (실기기 미검증)**: 아래쪽 N 눈금자(모바일 높이 24px)도 `safe-area-inset-bottom`을 반영하지 않는다. 홈 표시줄에 가려지는지 확인하고, 보정이 필요하면 배경 높이뿐 아니라 라벨 위치·클리핑·클릭 판정·`setSafeInsets.bottom`을 함께 바꾼다. 4번의 알약 높이 확대에 따른 N 눈금자 높이 점검은 별도로 필수다.

**완료 기준**
- 폭 360·390·430px 세로 화면에서 Z 0–118을 훑어 표시되는 라벨의 글자가 가로로 잘리지 않는지 검사한다. 4번의 충돌 규칙에 따른 라벨 생략과 글자가 경계에서 잘리는 현상을 구분한다. `118 Og`, `100 Fm`, `96 Cm`은 각각 선택해서 반드시 확인한다.
- iPhone 가로 화면에서 노치가 왼쪽에 있을 때와 오른쪽에 있을 때 모두 눈금자가 가려지지 않는다.
- 눈금자 위를 탭해도 지금처럼 핵종이 선택되지 않는다.
- 범례 칩과 지도 정보 알약이 눈금자와 겹치지 않는다.
- 웹 글꼴 로드 전후, 회전 전후에 눈금자·알약·라벨의 경계와 클릭 판정이 일치한다. 앱 글자 크기 설정을 제공하면 100–200%의 각 단계에서도 확인한다. 폰트가 늦게 로드되어도 이전 폭이 남지 않는다.

## 3. 원자번호 열: 번호와 원소 기호를 나눠 각각 오른쪽 정렬

**현재**
- `"92 U"`처럼 번호와 기호를 한 문자열로 만든다([rulers.ts:13](../src/chart/render/rulers.ts#L13)).
- 이 문자열을 통째로 오른쪽 정렬해서 그린다([rulers.ts:60](../src/chart/render/rulers.ts#L60), [:73](../src/chart/render/rulers.ts#L73)).
- 기호가 1–2글자이고 글자마다 폭이 달라서, 번호가 끝나는 위치가 줄마다 다르다. 번호가 세로로 맞지 않아 훑어 읽기 어렵다.

```
현재 (문자열 전체 오른쪽 정렬)      바꿀 모습 (두 칸, 각각 오른쪽 정렬)
      8 O                               8  O
     74 W                              74  W
     79 Au                             79 Au
    118 Og                            118 Og
```

**바꿀 모습**
- 번호 칸과 기호 칸을 나누고, 각 칸 안에서 오른쪽 정렬한다.
  - 번호 칸의 폭 `a`는 표시 가능한 Z 번호의 최대 실측 폭, 기호 칸의 폭 `b`는 원소 기호의 최대 실측 폭이다. 일반 500·마법수 700 등 실제 표시 상태를 포함하고 각각 올림한다.
  - 현재 앱은 [tabular-nums](../src/styles/global.css#L23)를 사용하므로 실제 캔버스에서 `104`와 `118`의 폭은 같았다. `118`이 더 좁다는 별도 캔버스 측정은 적용하지 않는다. 구현 시에도 실제 렌더링과 같은 글꼴·숫자 폭 설정으로 측정한다.
- 두 칸 사이 간격은 2번의 `g = f × 0.3`이다.
- 2번의 알약 시작점 `x`, 폭 `w`, 내부 여백 `p`를 사용한다. 기호 오른쪽 끝은 `x + w − p`, 번호 오른쪽 끝은 `기호 오른쪽 끝 − b − g`다.

**구현 메모**
- `Z_LABELS` 하나를 `Z_NUMBERS`와 `Z_SYMBOLS` 두 배열로 나누고, 라벨마다 `fill`을 두 번 호출한다.
  - 라벨 수는 화면 높이와 4번의 표시 간격·충돌 처리에 따라 달라진다. 문자열과 측정값을 캐시하고 기존 렌더링 성능 기준을 유지한다.
- 마법수 굵게(5번)와 선택 글자색은 두 칸에 모두 적용한다.
- `Z > 118`이거나 원소 표에 없는 Z는 번호 칸에만 쓴다. 해당 값이 표시 범위에 들어오면 번호 칸의 최대 폭 산정에도 포함한다.
- 폭이 늘어나므로 2번과 함께 구현한다.

**확인할 점**
- 두 칸 모두 오른쪽 정렬을 완료 기준으로 삼는다. 기호를 왼쪽 정렬하는 방식으로 바꾸면 이 기준과 달라지므로 이번 구현에 섞지 않는다.

**완료 기준**
- 화면에 보이는 모든 Z 라벨에서 번호의 오른쪽 끝 x좌표가 같다. 기호의 오른쪽 끝 x좌표도 같다.
- 데스크톱과 모바일, 라이트와 다크 테마에서 두 칸의 선택 색·마법수 굵기를 일관되게 적용한다. 호버와 이웃 라벨이 겹칠 때는 4번의 선택 우선 규칙을 따른다.

## 4. 원자번호 열에서 선택된 원소 상자를 가로로 넓히기

**현재**
- 선택한 Z는 강조색 알약으로 표시한다. 알약의 위치와 크기는 x = 3px, 폭 `눈금자 폭 − 6px`, 높이 16px로 고정이다([rulers.ts:47-52](../src/chart/render/rulers.ts#L47-L52), [:68](../src/chart/render/rulers.ts#L68)).
- 알약 폭이 라벨 폭과 상관없이 정해진다. 그래서 세 자리 번호에서는 글자가 알약 밖으로 나오고, 두 자리 번호에서도 좌우 여백이 거의 없다.
- 아래쪽 N 눈금자는 알약 폭을 `글자 폭 + 12px`로 정한다([rulers.ts:96](../src/chart/render/rulers.ts#L96)). 두 눈금자의 규칙이 다르다.

**바꿀 모습**
- 알약은 2번의 `x = s + m`, `w = c + 2p`를 사용한다. 노치 안전 영역을 제외한 곳에 그리며, 번호·기호 두 칸의 예약 영역을 기준으로 좌우 `p = max(6px, f × 0.5)`를 확보한다.
- 각 글자의 실제 잉크 폭은 다르므로 짧은 번호·기호에는 예약 칸 안에 여유가 남는다. "좌우 여백이 같다"는 조건은 개별 문자열의 잉크 경계가 아니라 두 칸의 예약 영역을 기준으로 한다.
- 알약 높이 `h = f + 8px`, 세로 시작점 `y − h / 2`로 한다. 기본 크기에서 모바일은 20px, 데스크톱은 21px다. 호버 알약도 같은 크기를 사용한다.

**표시 간격과 충돌 처리**
- 현재 [rulerStep](../src/chart/lod.ts#L9)은 Z 간격을 최소 16px로 정한다. `camera.s = 16`에서 인접 행의 선택·호버 알약을 20·21px 높이로 그리면 4·5px 겹친다. 폭 수정만으로는 해결되지 않는다.
- Z 눈금의 기본 최소 중심 간격을 `h + 2px` 이상으로 계산하도록 `rulerStep`에 실제 크기를 전달한다. 후보 간격을 고르는 것에 더해 최종 표시 경계도 검사한다.
- 선택·호버 라벨은 배수 눈금이 아니어도 그리는 현재 예외가 있으므로 눈금 간격만 바꿔서는 충분하지 않다. **선택 → 호버 → 나머지 눈금** 순서로 표시 공간을 예약한다. 이미 예약된 표시 경계와 2px 간격을 확보하지 못하면 낮은 우선순위의 눈금 라벨·알약을 생략한다. 선택과 충돌하는 호버 눈금은 생략하되 지도 칸의 호버와 툴팁은 유지한다. 같은 Z의 선택·호버는 선택 한 번만 그린다.
- 공통 알약 함수는 N 눈금자에도 쓰인다. N 알약 폭은 해당 숫자의 실측 폭 `+ 2p`, 높이는 같은 `h`로 계산한다. N의 기본 간격도 최대 알약 폭 `+ 2px` 이상으로 정하고, 선택·호버 예외에는 같은 우선순위로 가로 충돌을 처리한다.
- N 눈금자의 안전 영역을 제외한 표시 높이는 `max(기존 높이, h + 4px)` 이상으로 확보한다. 글자 크기 설정 변경 시에도 라벨·클리핑·클릭 판정·앱의 아래 여백을 함께 갱신한다.

**확인할 점**
- "가로 확장"을 이 문서는 "눈금자 안의 알약을 넓힌다"로 해석했다.
- 선택한 Z 행을 지도 쪽까지 띠로 이어 표시하려는 뜻이라면 작업이 따로 필요하다. overlay에 행 강조 띠를 추가해야 하며, 검색의 행 강조([overlay.ts](../src/chart/render/overlay.ts)의 `drawLineHighlight`)를 재사용할 수 있다.

**완료 기준**
- Z = 1, 26, 92, 118을 각각 선택했을 때 글자 전체가 예약 칸 안에 들어가고, 예약 영역과 알약 사이의 좌우 여백이 모두 `p` 이상이다.
- 데스크톱과 모바일 모두 같은 규칙으로 그린다.
- `camera.s = 16, 17, 18, 19, 20, 21`과 기본 눈금 간격이 바뀌는 경계에서 선택 Z와 이웃 Z를 호버한다. 배수 눈금 여부와 관계없이 선택 표시가 남고 라벨·알약이 겹치지 않는다. N 눈금자도 세 자리 숫자와 인접 선택·호버로 검사한다.
- 앱 글자 크기 설정을 제공하면 100–200%에서도 같은 기준을 만족해야 한다. 좁은 화면에서 호버를 지원하는 마우스 입력도 검사한다.

## 5. 마법수 번호: 초록색 대신 굵은 글씨만

**해석**
- 보고의 "안정원자번호"는 Z 눈금자에서 초록(청록)색으로 칠해진 **마법수** 2, 8, 20, 28, 50, 82(He, O, Ca, Ni, Sn, Pb)로 보았다.
- 마법수는 양성자나 중성자 수가 이 값일 때 핵이 특히 안정해서 강조하는 번호다.
- 다른 것을 가리킨 것이라면 이 항목을 다시 써야 한다.

**현재**
- 마법수 라벨은 굵게(700) 그리고 강조색으로 칠한다. 강조색은 라이트 테마 `#0F766E`, 다크 테마 `#2DD4BF`다.
  - Z 눈금자: [rulers.ts:70-72](../src/chart/render/rulers.ts#L70-L72)
  - N 눈금자: [rulers.ts:93-100](../src/chart/render/rulers.ts#L93-L100)
- 설계 [03 §6.4](03-visual-design.md#64-눈금자)에 "마법수 라벨은 굵게 + `--accent`"라고 정해 두었다.
- 강조색은 선택 알약과 버튼에도 쓰는 색이다. 그래서 마법수 라벨이 "선택됨"이나 "누를 수 있음"처럼 보인다.

**바꿀 모습**
- 선택되지 않은 라벨의 색은 마법수 여부와 관계없이 같은 `--text-muted`로 통일한다. 일반 라벨은 굵기 500, 마법수는 700으로만 구분한다.
- 종전 제안의 `--text`는 일반 라벨보다 진한 색이므로 "굵게만"이라는 기준과 다르다. 이번 수정에서는 추가하지 않고, 7번의 확대된 글자에서 굵기 차이를 시각적으로 확인한다.
- Z와 N 눈금자에 같은 규칙을 적용한다.
- 지도 위 마법수 선 라벨(`Z=50`)은 이미 `--text-muted`라서 바꾸지 않는다.
- 선택된 라벨은 지금처럼 알약과 반전 글자색을 쓴다.

**수정**
- [rulers.ts:72](../src/chart/render/rulers.ts#L72)와 [:100](../src/chart/render/rulers.ts#L100)의 색 분기를 `selected ? selectedText : theme.textMuted`로 바꾼다. `magic ? bold : normal` 글꼴 분기는 유지한다.
- [03 §6.4](03-visual-design.md#64-눈금자)의 문구를 고친다.

**완료 기준**: 라이트와 다크 테마에서 선택되지 않은 마법수·일반 라벨의 색이 같고, 굵기 700·500으로 구분된다. 선택 시에는 기존 강조 알약과 반전 글자색이 유지된다.

  - 지도 가용 영역 계산: [App.tsx:235](../src/app/App.tsx#L235) `sheet === 0 ? 144`
  - 줌 버튼·범례 위치: [global.css:1098](../src/styles/global.css#L1098) `bottom: 160px`는 현재 `144 + 16px`다. 새로운 시트 외곽 높이에 간격을 더한다.
- **칩 줄바꿈**: 태블릿 패널 폭 340px에서 칩 네 개(Z·N·A·범주)를 확인한다. 한 줄에 들어가지 않으면 줄바꿈을 허용하되 값이나 범주가 잘리거나 겹치면 안 된다.
- **설계 문서**: [03 §7.6](03-visual-design.md#76-정보-패널)의 헤더 글자 크기를 새 값으로 바꾼다.

**완료 기준**
- 기본 크기 100%에서 데스크톱·태블릿·모바일의 제안 크기가 적용된다. 앱에 100–200% 설정을 제공하면 이 값을 기준으로 확대한다.
- 모바일 시트 0·1·2단계를 각각 검사한다. "살짝" 단계에서는 스크롤 전에도 기호와 이름이 실제 콘텐츠 영역 안에 보이고, 나머지 내용은 스크롤로 접근할 수 있다. 펼친 시트에서는 칩·속성·닫기·이웃 이동 기능에도 접근할 수 있다.
- 긴 이름(예: `다름슈타튬-281`, `Rutherfordium-267`)과 영문 이름 옆 출처, 여러 줄 칩이 패널 내부에서 겹치거나 가로로 잘리지 않는다. 한국어·영어, 최소 화면 360×640, 태블릿 패널 폭 340px, 하단 안전 영역 유무, 200% 확대를 포함한다.
- 패널 외곽 검사뿐 아니라 이름·기호의 경계와 실제 보이는 콘텐츠 영역의 포함 관계를 검사한다. 스크롤 영역의 `scrollWidth`와 `clientWidth`도 비교하고 시각 확인을 병행한다.

## 7. 전체적으로 글씨 크기 키우기

**현재**
- [global.css](../src/styles/global.css)의 `font-size` 선언 63개 중 25개가 12px보다 작다(9px 1개, 10px 10개, 11px 14개). 12px은 17개다.
- 설계 [03 §2.2](03-visual-design.md#22-글꼴)의 크기 체계는 12 / 13 / 14 / 16 / 20 / 24 / 32px이다. 9–11px은 이 체계 밖이다.
- 캔버스 글자도 작다.
  - 눈금자: 모바일 10px, 데스크톱 12px([rulers.ts:29](../src/chart/render/rulers.ts#L29))
  - 마법수 선 라벨: 11px([guides.ts:126](../src/chart/render/guides.ts#L126))
  - 분기비 라벨: 12px([overlay.ts:180](../src/chart/render/overlay.ts#L180))

사용자가 자주 보는 작은 글씨는 다음과 같다.

| 위치 | 선택자 | 현재 |
|---|---|---|
| 지도 정보 알약 (핵종 수·출처) | `.map-meta` | 10px (모바일 9px) |
| 범례 행 / 개수 / 표식 설명 | `.legend-row` / `.legend-count` / `.legend-markers` | 12 / 11 / 10px |
| 패널 섹션 제목 | `.panel-section h3` | 11px |
| 패널 속성 라벨 / 값 | `.property dt` / `dd` | 12 / 13px (설계 13 / 14px) |
| 붕괴 분기 값 / 딸핵 없음 / 주석 | `.branch-value` / `.branch-target` / `.branch-note` | 11 / 10 / 10px |
| 배지 (추정·측정·미관측) | `.badge` | 10px |
| 이웃 이동 버튼 (N−1 등) | `.neighbor-controls button` | 11px |
| 출처 | `.panel-source p`, `.source-small` | 11 / 10px |
| 첫 방문 안내 | `.hint-card p` / `small` | 12 / 11px (모바일 11 / 10px) |
| 도움말 본문 | `.help-dialog p` | 12px |
| 앱 이름 부제 | `.brand p` | 11px |

**수정 방향**
1. **글자 크기 토큰을 만든다.** `:root`에 `--fs-xs`, `--fs-sm`, `--fs-md`, `--fs-lg` 같은 변수를 두고 UI 글자 크기를 토큰으로 바꾼다. `font-size`뿐 아니라 [진단 표시의 font 축약형](../src/styles/global.css#L469), 상속과 미디어 쿼리 재정의도 확인한다. 위첨자는 상대 크기 관계를 유지하되 예외로 명시하고 확대 시 가독성을 확인한다.
2. **최소 12px로 하고, 나머지는 한 단계씩 올린다.**

   | 현재 | 변경 |
   |---|---|
   | 9, 10, 11px | 12px |
   | 12px | 13px |
   | 13px | 14px |
   | 14px (본문) | 15px |
   | 16px 이상 (제목) | 6번 또는 개별 판단 |

   이 표는 기본 크기 100%의 일반 UI에 적용한다. 1번의 검색 입력·`select`는 최소 16px, 6번의 패널 머리글은 별도 제안값이 우선한다. 위첨자의 `0.58em`을 일반 본문 12px로 일괄 치환하지 않는다.

3. **캔버스 글자를 올린다.**
   - 눈금자는 기본 크기에서 모바일 10 → 12px, 데스크톱 12 → 13px로 올린다. [모서리 Z / N 표시](../src/chart/render/rulers.ts#L109)의 `fontSize - 1`도 12px 미만이 되지 않도록 바꾼다.
   - 2번의 폭 실측만으로는 충분하지 않다. 4번의 알약 높이·눈금 간격·선택과 호버 충돌 처리·N 눈금자 높이를 묶음 B에서 함께 바꾼다.
   - 마법수 선 라벨은 11 → 12px로 올린다.
   - 칸 안의 글자([labels.ts](../src/chart/render/labels.ts))는 칸 크기에 비례해서, 지도를 확대하면 커진다. 그래서 이번 범위에서 뺀다. 바꾸려면 LOD 경계([03 §5.2](03-visual-design.md#52-lod별-배치))도 다시 정해야 하므로 별도 항목으로 다룬다.
4. **고정 크기 레이아웃을 점검한다.** 글자가 커지면 넘칠 수 있는 곳들이다.
   - 모바일 머리글 한 줄(검색창 + 메뉴 버튼)
   - 범례 카드 폭 232px과 행 높이 26px(26px → 28px 검토)
   - 지도 정보 알약이 폭 360px 화면에서 한 줄에 들어가는지
   - 툴팁 최대 폭 250px
   - 설정 창 폭 282px
5. **설계 문서를 고친다.** [03 §2.2](03-visual-design.md#22-글꼴)의 크기 체계와, 03 §7의 컴포넌트별 크기를 바꾼다.
6. **UI 핀치를 차단한다면 100–200% 글자 크기 설정을 필수로 제공한다.**
   - 예를 들어 100 / 125 / 150 / 175 / 200%를 제공하고 모든 단계에서 정보와 기능을 잃지 않아야 한다. "보통 / 크게"라는 이름만 붙이고 실제 확대 범위를 정하지 않는 방식은 완료로 보지 않는다. UI 핀치를 유지한다면 앱 자체 설정은 선택이지만 사용자 확대 시 가독성과 기능은 여전히 검증한다.
   - CSS 토큰을 `rem`으로 정의하면 DOM 글자를 함께 키울 수 있다. 그러나 [TextCache.font](../src/chart/render/text.ts#L34)는 px 글꼴을 직접 만들므로 루트 글자 크기만 바꿔도 캔버스가 자동으로 커지는 것은 아니다.
   - 설정 배율을 눈금자·마법수 선·분기비 등 캔버스 보조 글자에도 전달하고, 최종 크기를 기준으로 2·4번의 폭·높이·간격과 앱 가용 영역을 다시 계산한다. 칸 내부 라벨은 기존 지도 줌으로 확대하는 별도 체계를 유지한다.
   - 6번의 시트 높이, 검색·설정·도움말·범례·툴팁도 같은 확대 설정에서 검사한다. 기본 글자를 12px로 바꾸는 작업은 이 확대 기능의 대체가 아니다. [W3C Resize Text](https://www.w3.org/WAI/WCAG21/Understanding/resize-text)는 200%까지 내용·기능 손실 없는 텍스트 확대를 요구한다.

**완료 기준**
- 일반 UI의 계산된 글자 크기가 12px 이상이고 검색 입력·`select`는 16px 이상이다. 토큰·`font` 축약형·미디어 쿼리까지 확인한다. 위첨자는 명시된 상대 크기 예외로 따로 검사한다. CSS 숫자 문자열 검사만으로 완료로 보지 않는다.
- 폭 360×640 모바일, 844×390·932×430 가로 화면, 1280×720 데스크톱에서 겹침·잘림·의도치 않은 가로 스크롤이 없다. 한국어·영어와 라이트·다크 테마에서 확인한다.
- 기존 E2E `모바일 시트가 뷰포트 안에 있고 가로 스크롤이 없다`([nuclide-map.spec.ts:146](../e2e/nuclide-map.spec.ts#L146))는 유지하되 통과만으로 완료로 보지 않는다. 이 테스트는 기본 시트 1의 외곽과 페이지 가로 폭만 검사한다. 검증 때 제목을 의도적으로 크게 만들어 내부에서 잘리게 해도 외곽 검사 조건은 통과했다.
- 시트 0·1·2의 내부 경계, 긴 이름과 칩 줄바꿈, 설정 창과 검색 결과, 펼친 범례와 도움말의 스크롤을 검사한다. 캔버스는 DOM 크기로 라벨 잘림을 알 수 없으므로 실제 텍스트 측정값·그리기 경계 검사와 스크린샷을 함께 사용한다.
- UI 확대 방식별로 200%까지 내용·기능 손실이 없는지 확인한다. 앱에 확대 단계를 제공한다면 모든 중간 단계도 검사한다. 이 검증이 끝나기 전에는 1번의 전역 UI 핀치 차단을 적용하지 않는다.

## 공통: 검증 환경

- **실기기가 필요하다.**
  - 1번(iOS 자동 확대)과 2번(실제 노치·홈 표시줄)은 데스크톱 모바일 에뮬레이션의 통과로 검증 완료를 주장하지 않는다. 안전 영역 값을 주입한 테스트는 계산 경로만 검증한다.
  - iPhone Safari(세로·가로, 좌우 노치 방향)와 Android Chrome에서 각각 한 대 이상 확인하고 기기·OS·브라우저 버전을 기록한다. 지원 버전 정책은 01 NFR-04를 따른다.
- **Playwright에 iPhone 프로젝트를 추가한다.**
  - 지금 모바일 E2E는 Pixel 7(Chromium) 하나뿐이다([playwright.config.ts:31](../playwright.config.ts#L31)).
  - `devices['iPhone 14']`(WebKit) 프로젝트를 추가하면 WebKit 모바일 레이아웃 회귀를 잡을 수 있다.
  - [Playwright의 WebKit 설명](https://playwright.dev/docs/browsers#webkit)처럼 해당 엔진은 실제 Safari와 동일한 실행 환경이 아니다. 자동 테스트와 실기기 결과를 별도로 남긴다.
- **눈금자와 글자 크기 변경(2–7번)은 화면으로 확인한다.** 시각 회귀 테스트는 아직 없다([PROGRESS.md](PROGRESS.md)). 도입할 때 모바일 Z 100 이상 구간, 인접 선택·호버, 마법수, 시트 0·1·2, 한국어·영어와 200% 확대 화면을 기준 스크린샷에 넣는다. 글꼴 로드를 기다린 뒤 촬영하고, 느린 글꼴 로드 중 폭 갱신은 별도 검사한다.
